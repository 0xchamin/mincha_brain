| n1 | **The 2025-11-25 protocol made a client stateful by construction, and the state lived in one process.** An HTTP client had to complete an `initialize` handshake; the server returned an `Mcp-Session-Id` header; every later call had to carry it, "pinning the client to the specific container or pod that held its **in-memory** session state". | prose, §Why Sessions Were a Production Bottleneck | artifact - the legacy handshake block: `"method": "initialize"` with `protocolVersion`, `capabilities` and `clientInfo` exchanged **once**, in `params` | corroborated | OK |
| n2 | **The failure was not degradation, it was a hard error on the second request.** Three pods behind a standard round-robin load balancer: "a second request from a client would randomly hit another pod, returning a **400 Session Not Found** error". Named consequences: sticky-affinity rules that defeat even distribution and make autoscaling inefficient; a pod restart losing session state instantly; and remote servers needing shared Redis stores or gateway packet inspection. | prose, §Why Sessions Were a Production Bottleneck, four bullets | (none - no artifact, no trace, no reproduction) | single-leg | needs-check. **Specific enough to be checkable and not checked here** - the article gives no repro, no configuration and no measurement. | n3 | **The fix is that the handshake was deleted, and the state it carried now rides on every request.** `initialize`/`initialized` removed (SEP-2575), `Mcp-Session-Id` removed (SEP-2567); protocol version, client info and client capabilities "now travel in a `_meta` field inline on every single request". | prose, §The New Request Model | artifact - **the two payloads diff cleanly**: the same three fields (`protocolVersion`, `clientCapabilities`/`capabilities`, `clientInfo`) appear in the legacy `initialize` `params` and again in the new request's `_meta`, namespaced `io.modelcontextprotocol/` | **corroborated, and this is the strongest artifact-level corroboration in the source** - the relocation is visible field by field | OK on the mechanism. **The SEP numbers are prose-only** and were not checked against the spec |
| n4 | **Routing metadata was promoted out of the JSON-RPC body into HTTP headers, and the two are required to agree.** `Mcp-Protocol-Version`, `Mcp-Method` (e.g. `tools/call`) and `Mcp-Name` (the specific tool, prompt or resource). "These headers are mirrored to match the JSON-RPC body. | n5 | **The point of the headers is that intermediaries stop needing to read bodies.** "proxies, gateways, and load balancers can route, rate-limit, and audit traffic without inspecting the request body", which the article calls a win for security and logging teams and says "drastically lowers the latency and processing overhead at the gateway layer". | prose, §No More Deep Packet Inspection | artifact - the header set is sufficient for the stated use: a gateway can rate-limit by `Mcp-Name` without parsing JSON | corroborated on the mechanism | OK on the mechanism; **needs-check on "drastically"** - no latency or throughput figure appears anywhere in this article |
| n6 | **Cacheability was added so clients stop holding SSE connections open just to watch for change.** Tool and resource results may return `ttlMs` and a `cacheScope`, "modeled after HTTP's Cache-Control", so a client knows how long a `tools/list` response is fresh "and whether it is safe to cache across multiple users" (SEP-2549). | prose, §Intelligent Caching with ttlMs | (none - no example, no field placement, no default) | single-leg | needs-check. **The one substantial feature in the article with no artifact at all.** `cacheScope` across users is a security-relevant field described in half a sentence |
| n7 | **Server-to-client questions were made stateless by handing the state to the client.** Previously an elicitation needed a held-open SSE connection. Under MRTR (SEP-2322) the server "immediately returns an `InputRequiredResult` with a `requestState` payload containing serialized context"; the client prompts the user and "reissues the call with `inputResponses` and the echoed `requestState`". "Because the `requestState` contains everything needed to resume the task, **any server instance behind your load balancer can pick up the retry request**." | prose, §Multi Round-Trip Requests | artifact - the `InputRequiredResult` block: `resultType`, an `inputRequests` map holding an `elicitation` with message and schema, and `requestState` as an opaque string | corroborated | OK |
| n8 | **In the article's own example that client-held state is unauthenticated plaintext.** The `requestState` value `eyJzdGVwIjoxLCJmaWxlcyI6WyJhIiwiYiIsImMiXX0=` decodes to `{"step":1,"files":["a","b","c"]}` - 32 bytes, no signature, no MAC, no ciphertext. The elicitation it accompanies is **"Are you sure you want to delete these 3 files?"**, so the file list the server will act on is carried, outside the server, by the party the confirmation exists to check. | artifact - base64-decoded during this pass; see `SOURCE.md` ingest notes | prose confirms the custody and the round trip - "the client... **reissues** the call with... the **echoed** `requestState`" - and **never mentions integrity, signing or encryption anywhere** | **corroborated on custody** (prose + artifact agree the client holds and returns it); **single-leg on the plaintext** (artifact only) | OK on both facts. **The consequence is this brain's reading, not the article's** - see `d1`, and see the open question about what the spec requires |
| n9 | **Long-running work was made non-blocking by returning a handle instead of a result.** The Tasks extension (SEP-2663) graduates from experimental to a first-class extension: for work taking "anywhere from 10 to 60 seconds" - a database backup, a CRM sync, a payment refund - the server returns a `taskId` immediately and executes in the background; the client polls or subscribes via `tasks/get` and `tasks/update`. | prose, §The Tasks Extension | artifact - the TypeScript handler mints `randomUUID()`, calls `processRefundAsync(...)` without awaiting it, and returns `{ taskId, status: "working", ... }` in `content` | corroborated | OK |
| n10 | **Statelessness here is state relocation, three times, to three different owners - and the article states the general form itself while its headline denies one instance.** Session state moved **to the wire** (`_meta` on every request, `n3`); elicitation state moved **to the client** (`requestState`, `n7`); long-running task state moved **to the application** (`n9`). ## Dropped / divergences (audit trail)

| The security section against its own MRTR example | **divergence** `d1` | **The sharpest finding in this source, and it is an absence rather than a contradiction.** The article devotes a section to security and addresses three things: issuer verification, resource indicators and schema strictness (`n11`, `n12`). All three are **inherited OAuth and JSON concerns**. The one trust surface the redesign **newly created** - server execution state serialized, handed to the client, and taken back on faith (`n7`, `n8`) - is not mentioned in it, or anywhere. The article's own framing makes the omission conspicuous: it says responsibility for state "shifts from the transport layer to the application layer" and that this is why "security becomes paramount", then secures the layer that did not change. **Recorded, not resolved.** The article shows an illustrative example, not a spec requirement, and this pass did not read the spec - so the honest statement is that **the article gives a reader no reason to believe `requestState` is protected, while showing them an unprotected one guarding a delete.** Whether the 2026-07-28 spec mandates integrity protection is this source's number-one research target. |
| "No Redis Sessions Needed" against the Tasks example | **divergence** `d2` | The stateless-core bullet list says: "**No Redis Sessions Needed**: Major production servers, such as the GitHub MCP Server, have already upgraded to this spec and completely removed Redis session storage, eliminating database writes and reads on every single call". Four sections later, the Tasks extension example contains the line `// Store initial task state in a shared datastore (e.g. **Redis**)` followed by `await setTaskState(taskId, { status: "working" })`. **Both are true and the headline is the misleading one.** What was removed is Redis as a *transport session store*, keyed by connection and required on every call; what remains is Redis as an *application task store*, keyed by work and required only for async operations. That is a real and large improvement. It is not the elimination the bullet implies, and a reader planning capacity from the bullet alone will not provision the store their own long-running tools need. Feeds `n10`. |
