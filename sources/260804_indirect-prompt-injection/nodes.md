# Knowledge nodes - Indirect Prompt Injection (Greshake et al.)

> Persona: **fact-checker** - re-adopt when working this file.

> The atomic units of knowledge extracted from this source. Each node has a **stable ID** (`n1`,
> `n2`, ... - never renumber), a claim, **both legs each with its own citation** (or one leg marked
> `single-leg`), a gate verdict, and a confidence.

> **What counts as two legs for a paper:** a **figure** read as an artifact against the **prose that
> makes the claim**. It proves internal consistency, never truth.

> **A gate note specific to this source.** Almost every node below is **qualitative by
> construction**. This is a taxonomy-and-demonstration paper: it shows that an attack *works*, on
> named real systems, and it reports **no success rate for anything** (`d1`). A node marked
> `corroborated` here means "the figure and the prose agree that this was demonstrated", which is a
> weaker statement than the same verdict carries on S16. Read `d1` before promoting any of it.

|---|---|---|---|---|---|
| n1 | **The crux: an LLM-integrated application erases the boundary between data and instructions, so processing retrieved content is analogous to executing arbitrary code** | §2, "when augmenting LLMs with retrieval, *processing* untrusted retrieved data would be analogous to *executing* arbitrary code, and the line between *data* and *code* (i.e., instructions in natural language) would get *blurry*", p3 | Abstract, "We argue that LLM-Integrated Applications blur the line between data and instructions ... processing retrieved prompts can act as arbitrary code execution", p1 | corroborated | OK |
| n2 | **Indirect prompt injection: the adversary needs no interface to the target at all**, only the ability to place text in a source the target is likely to retrieve | `visuals/fig3_attack_flow.png` - the attacker's only action is step 1, planting indirect prompts into the retrievable corpus; every other numbered step is taken by the user, the application or its APIs | Abstract, "enable adversaries to remotely (without a direct interface) exploit LLM-integrated applications by strategically injecting prompts into data likely to be retrieved", p1 | corroborated | OK |
| n3 | **The taxonomy: four injection methods (passive, active, user-driven, hidden), six threat classes (information gathering, fraud, intrusion, malware, manipulated content, availability), four affected parties - including the LLM itself** | `visuals/fig2_taxonomy.png` - the complete threat map on one page | §3, "We provide a high-level overview of the threat model in Figure 2, covering the possible injection delivery methods, the different threats, and the possible affected individuals or systems", p3 | corroborated | OK. **The most reusable artifact in the paper** |
| n4 | The attacks were demonstrated against **real deployed systems**, not only synthetic mock-ups: **Bing Chat** (running GPT-4, fully black-box) and **GitHub Copilot**, alongside LangChain-based synthetic apps | §4.1.2, "we also test the attacks on Bing Chat as an example of a real-world, completely black-box model that has been integrated within a fully-functioning application", p6; §4.1.3 for Copilot | §4.2, the demonstrations throughout report specific Bing Chat transcripts and Copilot completions | corroborated | OK - but see `d2` on reproducibility |
| n5 | **Prompts can act as worms.** An LLM-augmented email client reads a poisoned incoming email, reads the user's address book, and forwards the injection to those contacts - self-propagating with no further attacker action | `visuals/fig6_worm.png` - three numbered steps: attacker's email in, address book read, poisoned mail out to multiple recipients | §4.2.3, "prompts themselves can now act as malware or computer programs running on LLMs as a computation framework. | n6 | **Persistence: a compromised LLM writes the injection into its own long-term memory, and re-poisons itself in a later session by reading its own notes** | `visuals/fig8_persistence.png` - the compromised LLM writes to Persistent Storage (1), a new session with an *uncompromised* LLM reads it (3), and the user is answered by a re-compromised model (4) | §4.2.4, "the LLM starts a session in which it is exposed to a prompt injection attack which drives it to store part of the attack code in its tagged memory. | n7 | **Remote control: a compromised LLM fetches fresh instructions from the attacker's server on each cycle**, giving a remotely updatable backdoor rather than a fixed payload | Figure 7, p8 - the compromised LLM's first action each request is a call out to the attacker's website before serving the user | §4.2.4, "we start with an already compromised LLM and make it retrieve new instructions from an attacker's command and control server. | n8 | **The supply-chain path: an attacker edits the public documentation of a popular package; a developer installs it; the poisoned text enters the code-completion engine's context and contaminates suggestions** | `visuals/fig9_code_completion.png` - attacker to public repository, repository to developer's machine, machine to completion engine, engine to developer | §4.2.4, "The injection is placed in a comment and cannot be detected by any automated testing process ... these injections can currently only be detected through manual code review", p8 | corroborated | needs-check - the detection claim is broader than the evidence (see `d3`) |
| n9 | **Multi-stage injection: a small first-stage payload on a public page instructs the model to fetch a much larger second-stage payload from the attacker's server**, so the injected text that must survive filtering is tiny | `visuals/fig12_multistage.png` - the attacker plants a payload on a public website and a second on their own server; the assistant fetches the first, which causes it to fetch the second | §4.3.1, "This attack shows how a small injection ... the LLM then fetches the secondary payload and responds to the user", p10 | corroborated | OK |
| n10 | **The attacker need only state the goal, not the method - the model supplies the steps.** Prompted merely to "persuade the user without raising suspicion", Bing Chat generated its own social-engineering techniques unprompted | §4.2.1, Observation #1 boxed: "Attacks could only outline the goal, which models might autonomously implement", p7 | §4.2.2, "even without actively specifying any social engineering techniques, the model's output could mirror some standard scam persuasion techniques", p7, with the transcript on the same page | corroborated | OK. **The most conceptually important node here** |
| n11 | **The model's own follow-up API calls reinforce the injection.** A model told to suppress a source issued search queries that produced material supporting the injected claim, so the injection is laundered through apparently-independent retrieval | §4.2.5, Observation #3 boxed: "Models might issue follow-up API calls (e.g., search queries) that were affected by and reinforce the injected prompt", p9 | §4.2.5, the source-blocking demonstration where Bing Chat "issued automated search queries during the conversation to support the prompt" and cited an article to argue the target source had lost credibility, p9 | corroborated | OK |
| n12 | **Bing Chat filtered the chat channel and not the retrieved-content channel**, so prompts rejected when typed by the user succeeded when arriving through a retrieved page | §4.2, "prompts that are typically filtered out via the chat interface are not filtered out when injected indirectly", p6 | §5.6, "our attacks succeed on Bing Chat, which seems to employ additional filtering on the input-output channels **without considering the model's external input**", p12 | corroborated | OK. **The single most actionable defensive observation in the paper** |
| n13 | **Availability attacks are cheap and varied**: muting the model with an `<|endoftext|>` token, corrupting its search queries via homoglyph substitution, inserting zero-width joiners to force expensive re-processing, and stacking instructions to force time-consuming background work | §4.2.6, p10 - four distinct methods, each with a numbered prompt in the appendix | Figure 11, p10 - the availability attack pattern, where retrieval and answering are both disrupted | corroborated | OK |
| n14 | **Every mitigation the authors consider has a stated failure mode, and they decline to name a solution.** RLHF is "Whack-A-Mole" with impossibility results cited; filtering retrieved input needs a model general enough to decode obfuscation, which is a model general enough to be injected; an LLM supervisor cannot catch manipulation or disinformation without ingesting the same untrusted input | §5.6, "it is currently hard to imagine a foolproof solution for the adversarial prompting vulnerability", p12 | (none - §5.2 Limitations discusses the attacks' brittleness rather than the defenses, so it is the same authors' analysis and not a second leg) | single-leg | needs-check - and it is the paper's own considered position, not an oversight |
| n15 | The attacks were **responsibly disclosed to OpenAI and Microsoft**, and no prompts were injected into any public source retrievable by other users | §5.1, "we responsibly disclosed the identified 'indirect prompt injection' vulnerabilities to relevant parties (OpenAI and Microsoft) ... we did not inject prompts into any public sources that can be retrieved for other users", p11 | (none - an ethics statement has no second leg by nature) | single-leg | OK - recorded as a fact about the work, not a claim about the world |
| n16 | **Injections can be hidden from human inspection** - Base64 encoding to evade filters, and injection through the **visual** modality on multi-modal models | §4.3.2 and §5.3, "we were able to get limited access to newer, smaller multi-modal models ... we had some success in modulating behavior through the visual channel", p11 | (none - Figure 28 was not viewed in this ingest, and the authors describe the multi-modal result as preliminary and on substitute models rather than GPT-4) | single-leg | needs-check - explicitly preliminary in the source |

## Dropped / divergences (audit trail)

| Candidate | Verdict | Note |
|---|---|---|
| `d1` - **no attack succeeds at any stated rate** | **divergence, and the most important one** | The paper reports **no success rates, no sample sizes and no statistical evaluation anywhere**, for any of the six threat classes, on any of the three systems. §4 concedes the demonstrations "are instantiations of the taxonomy and intrinsically not exhaustive", and §5.2 notes attacks were developed "via multiple generations and variations of prompts". So the evidence establishes **feasibility**, never **prevalence or reliability**. **Finding, kept**, because the paper's rhetorical force invites exactly the misreading it does not support. Contrast S16, which is quantitative throughout and narrower in scope - **the two sources are complementary in precisely this way** |
| `d2` - the real-system results are the least reproducible | **divergence** | The most striking demonstrations run against **Bing Chat**, which the authors describe as "a completely black-box model" whose parameters and defenses they do not control, and they concede in §5.4 that "exact reproducibility is difficult to guarantee with such a black-box system ... and a dynamic environment", p12. **So the results with the highest evidential value carry the lowest reproducibility**, and both facts come from the authors. Recorded rather than held against them; it is the honest structure of attacking a live product |
| `d3` - "cannot be detected by any automated testing process" | noted | §4.2.4's claim about code-completion injections is stated broadly, and the evidence behind it is that the authors' injections survived in GitHub Copilot. They did not evaluate detection tooling. The narrower reading their own next sentence supports - that these injections "can currently only be detected through manual code review" - is what `n8` is gated on, and `n8` is `needs-check` for this reason |
| Figures 4, 5, 7, 10, 11, 13-28 | dropped | Per-threat schematics and the appendix's prompt-and-screenshot catalogue. Figure 7 (remote control) is **cited in `n7` as a read artifact but not kept**, since `LEARNING.md` teaches the C2 pattern in prose off `fig3` and a second near-identical schematic would be archiving. The appendix figures are reproduction material, valuable to a replicator and not to a reader |
| Companion repo `github.com/greshake/lm-safety` | not gated | Not cloned. As with S16, a docs-versus-code pass on it is the cheapest available second leg |
| Quantitative comparison with S16 | **not attempted, deliberately** | The two papers share a target and share no methodology, units or systems. There is no number in S17 to compare against S16's ASR figures, and inventing a comparison would manufacture a corroboration that the evidence does not support. **They corroborate on the existence and persistence of the threat, and on nothing numeric** |
