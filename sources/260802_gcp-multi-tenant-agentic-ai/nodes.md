> Persona: **fact-checker** - re-adopt when working this file.

> The atomic units of knowledge extracted from this source. Stable IDs (`n1`, `n2`, ... - never
> renumber). Only `corroborated` / `single-leg` nodes and recorded `divergence` findings feed

**Legs for this source.** Leg A is the article prose; Leg B is the single architecture figure
(`visuals/fig1_architecture.png` and its two crops - **one figure, three views, still one leg**).
Two prose sections agreeing is **one** leg, which bites here: the document states each component
once under *Architecture* and again under *Design considerations*, and the restatement is not
corroboration.

**A structural weakness in this source's gate, worth knowing before reading a single verdict.** Both
legs are the same author team on the same page. A `corroborated` node here means the diagram and the
text agree, which is a check on *this document's internal consistency* and no evidence whatever
about the world. On a source whose figure is a benchmark chart or a console screenshot, the second
leg is at least a different **kind** of artifact; here it is the same claim drawn instead of typed.
Read every `OK` below as "the document is consistent about this", never as "this works".

## Dropped / divergences (audit trail)

| Candidate | Verdict | Note |
|---|---|---|
| The figure's VPC box vs the prose's org-level perimeter | **divergence** `d1` | The prose makes VPC Service Controls the outermost claim in the document - "a service perimeter at the **organization** level... a strict security boundary and it prevents data exfiltration" - and the Security section names it as one of the three things you combine for tenant isolation. **The figure draws a "VPC" box around the shared hubs only.** The tenant projects sit outside it; no perimeter is drawn around them, around the pair, or around the organization. Most likely a diagram simplification (a network VPC and a VPC-SC perimeter are different objects sharing three letters), but the consequence for a reader is real: **the boundary the text leans on hardest is the one boundary the picture does not contain**, and someone building from the diagram ships project isolation plus PAB and no exfiltration control. Recorded, not resolved. |
| Security section vs cost section on Model Armor | **divergence** `d2` | **The sharpest internal tension in the document, and both sides sit in the same paragraph.** The architecture deploys Model Armor twice "To enforce strict governance and a zero-trust posture"; the cost section then says "Although this two-layered approach helps to ensure data sovereignty, it increases latency and operational costs. To reduce costs and system complexity, filter all of the prompts and responses by deploying Model Armor **exclusively in the routing hub**." The recommendation deletes the *tenant-local* leg and keeps the *shared* one - so under the cost-optimised variant **every tenant's PII masking happens in shared infrastructure**, which is the precise thing "data sovereignty" is invoked to protect against, and the sentence concedes it in the clause before. Neither option is wrong; presenting the swap as an unqualified cost tweak is. The missing artifact is the **condition** - which tenants may drop the local filter - and the document never supplies it. |
| The compromise guarantee vs the recommended variants | **divergence** `d3` | The use case states it flat: "Even if an agent identity is compromised, the agent can't access unauthorized Google Cloud resources." That holds for **the fully-local topology the figure draws**. It does not hold unqualified for the variants the same document recommends: a **shared MCP server** reachable from several tenants moves enforcement into "robust identity propagation and authorization logic" that is never specified (`n11`), and a **shared model endpoint** puts tenants in one quota pool needing "mitigation strategies" against abuse. The guarantee appears in the Use case section; the qualifications appear three sections later under Design alternatives, with no cross-reference. **A guarantee that silently depends on which alternatives you took is the failure mode reference architectures are most prone to.** |
| No evals, anywhere | **gap** `g1`, recorded not promoted | ~5,000 words on running agents for enterprise business units and **the word "eval" does not appear**. Observability is entirely infrastructural - Cloud Logging, Monitoring, "monitor the health and performance of the entire platform", "set up alerts to proactively detect and troubleshoot issues". There is no per-tenant answer-quality signal, no regression gate, nothing about whether the electronics agent is *right*. Against S1 (log the flat trace first, then per-stage metrics) and S5 (don't ship skills without evals), the absence is notable. **Not promoted to `evals.md`, and S12 is not counted as an evals source** - an absence is not a source ([ADR-0012](../../brain/decisions/0012-a-mention-is-not-a-source.md)), and reading silence as a claim is exactly the laundering that ADR exists to prevent. Kept here and in `LEARNING.md` as an observation. |
| No path between tenants, and no discussion of wanting one | **gap** `g2` | The architecture makes cross-tenant access structurally impossible and never asks what happens to a request that legitimately spans two business units - "I bought a TV and a sofa, where are my orders?" No A2A, no cross-tenant orchestration, no supervisor agent, no shared conversational state. The system is *n* independent agents behind one door, not a multi-agent system. That may be the right call; the document does not make it as a call. |
| No memory | **gap** `g3` | Session context appears only as a **cost** problem to be summarised away (`n17`). Nothing persists between sessions, nothing is said about whether per-tenant memory would be a further isolation boundary, and nothing addresses the injection surface a shared store would create. Given that this brain holds two vendor sources treating memory as core agent architecture (S6, S7), a 2026 enterprise reference architecture with no memory tier is worth recording. |
| Server-side rendering over client-side rendering | dropped | Real advice, correctly argued (secrets stay server-side, smaller client attack surface, centralized output encoding against XSS), but it is **generic web application security** that would read identically in a reference architecture for a shopping cart. Nothing about it is agent-specific. Signal, not archive. |
