| n3 | The protocol's seven core terms are **renames of ordinary things**: resource owner = the user, client = the app, authorization server = where you consent, resource server = the API holding the data, plus authorization grant, redirect URI, access token. | `visuals/frame_960.jpg` - slide "OAuth 2.0 terminology" listing all seven | narration "a bunch of terms and jargon that basically just renames things that we already have names for" @ [&t=973s](https://www.youtube.com/watch?v=996OiexHze0&t=973s) | corroborated | OK |
| n4 | **The authorization code flow is the whole protocol**; everything else in the spec is a variation on it. Redirect to the authorization server with redirect URI + response type + scopes -> user authenticates and consents -> redirect back with a code -> exchange code for an access token -> call the API with the token. | `visuals/frame_1840.jpg` - slide "OAuth 2.0 authorization code flow" showing the full round trip | narration "this whole flow here, this is the whole thing. The entire rest of this talk we're basically just going to be talking about slight variations" @ [&t=1323s](https://www.youtube.com/watch?v=996OiexHze0&t=1323s) | corroborated | OK |
| n5 | **The two-step code exchange exists because the browser is a front channel.** The code crosses the browser where it can be observed, but is useless alone: redeeming it requires the `client_secret` over a back channel, which never touches the browser. | `visuals/frame_2415.jpg` - slide "Exchange code for an access token": `POST .../token` carrying `code`, `client_id`, **`client_secret`**, `grant_type=authorization_code` | narration "even if someone stole the authorization code, they wouldn't be able to make that exchange request ... because they don't have that secret key ... we don't ever want that secret key to be in the browser" @ [&t=1937s](https://www.youtube.com/watch?v=996OiexHze0&t=1937s) | corroborated | OK |
| n6 | The flow is **deliberately split across both channels to use each for what it is good at**: the front channel (browser) for interacting with the human - login, consent - and the back channel (server to server) for anything secret. | `visuals/frame_1840.jpg` - the same flow slide annotated "(front channel)" on the redirects, with the exchange left unannotated | narration "the front channel here is used to interact with the user ... but because we can't completely trust the browser with like secret keys, we let the last step, the exchange, happen on the back channel" @ [&t=1989s](https://www.youtube.com/watch?v=996OiexHze0&t=1989s) | corroborated | OK |
| n7 | **Scopes are the granularity mechanism**, and they do double duty: the client enumerates them up front, they generate the text of the consent screen, and the issued access token is bound to exactly those scopes. | `visuals/frame_1500.jpg` - flow slide with `Scope: profile contacts` in the initial request; `visuals/frame_1240.jpg` - the resulting consent screen "Allow Yelp to access your public profile and contacts?" | narration "that access token itself is limited or scoped to exactly what scopes were requested at the beginning ... Yelp couldn't turn around and go send some other API request" @ [&t=1549s](https://www.youtube.com/watch?v=996OiexHze0&t=1549s) | corroborated | OK |
| n8 | There are **four grant types, and the split is exactly which channels they use**: authorization code (front + back), implicit (front only), resource owner password credentials (back only), client credentials (back only). | `visuals/frame_2520.jpg` - slide "OAuth 2.0 flows" listing all four with the channel annotation on each | narration "there are a couple of different OAuth grant types ... those two flows are back channel only" @ [&t=2597s](https://www.youtube.com/watch?v=996OiexHze0&t=2597s) | corroborated | OK |
| n9 | The **implicit flow** exists for clients with no back channel (a pure JS single-page app): `response_type=token` returns the access token straight to the browser, skipping the exchange. | `visuals/frame_2660.jpg` - slide "OAuth 2.0 implicit flow", `Response type: token`, token returned direct to a "Yelp Angular app" | narration "if for some reason you don't have a back channel, you only have a front channel, then you can skip that exchange step" @ [&t=2530s](https://www.youtube.com/watch?v=996OiexHze0&t=2530s) | corroborated | OK |
| n10 | **Client credentials** is the machine-to-machine grant: no user, no browser, back channel only. | (no dedicated slide beyond the list in `frame_2520.jpg`) | narration "the client credentials flow is sometimes used when you're doing like machine to machine or service communication" @ [&t=2613s](https://www.youtube.com/watch?v=996OiexHze0&t=2613s) | single-leg | needs-check |
| n11 | OAuth 2.0 became **a victim of its own success**: the industry adopted it for authentication (the social login buttons, ~2009-2010) although it was never designed for that. | (no dedicated slide in the kept set) | narration "it kind of became a victim of its own success ... OAuth was never designed to be used for authentication" @ [&t=2824s](https://www.youtube.com/watch?v=996OiexHze0&t=2824s) | single-leg | needs-check |
| n12 | **The concrete defect: OAuth has no standard way to return who the user is.** It reasons about permissions, not identity - so every provider bolted on a proprietary way to fetch user info, and the "standard" stopped being interoperable. | (no dedicated slide in the kept set) | narration "there is no way in the OAuth protocol to get the user's information ... they all had to add their own kind of custom hacks on top of OAuth" @ [&t=2894s](https://www.youtube.com/watch?v=996OiexHze0&t=2894s) | single-leg | needs-check |
| n13 | **OpenID Connect is a thin layer on OAuth 2.0, not a competitor** - "a 5-10% layer on top" that closes the authentication gap. It is stacked on OAuth exactly as OAuth is stacked on HTTP. | `visuals/frame_2985.jpg` - slide "OAuth 2.0 and OpenID Connect" showing the layer cake OpenID Connect / OAuth 2.0 / HTTP, captioned "OpenID Connect is for **authentication**, OAuth 2.0 is for **authorization**" | narration "it's really just a 5 10% layer on top of OAuth 2.0 ... OpenID Connect isn't really new, it's just an extension to OAuth 2.0" @ [&t=2979s](https://www.youtube.com/watch?v=996OiexHze0&t=2979s) | corroborated | OK |
| n14 | OIDC adds **an ID token and a userinfo endpoint**, and on the wire the *only* thing that makes a request an OIDC request is asking for the **`openid` scope**. | `visuals/frame_3080.jpg` - slide "OpenID Connect authorization code flow", identical to the OAuth one except `Scope: openid profile` and a "Log in with Google" button | narration "the only difference ... now we're also asking for this other scope called openid. And that is the only thing that means that this is an OpenID Connect request" @ [&t=3072s](https://www.youtube.com/watch?v=996OiexHze0&t=3072s) | corroborated | OK |
| n15 | **The ID token is a JWT** - header, payload (claims), signature - and the signature lets the client verify the token was issued by that authorization server and not modified, **without a call back to the server**. | `visuals/frame_3285.jpg` - slide "The ID token (JWT)" showing `(header)` / claims `iss`, `sub`, `name`, `aud`, `exp`, `iat`, `auth_time` / `(Signature)` | narration "the ID token because of that signature can be kind of independently verified by the application without even necessarily having to go back and talk to the authorization server" @ [&t=3347s](https://www.youtube.com/watch?v=996OiexHze0&t=3347s) | corroborated | OK |
| n16 | **The rule for choosing:** OAuth 2.0 for granting access to APIs and user data (authorization); OpenID Connect for logging a user in (authentication). OIDC does not replace OAuth - **it replaces misusing OAuth for authentication.** | `visuals/frame_3410.jpg` - slide "OAuth and OpenID Connect": two columns, "Use OAuth 2.0 for ... (Authorization)" vs "Use OpenID Connect for ... (Authentication)" | narration "the only thing that OpenID Connect replaces is misusing OAuth for authentication" @ [&t=3416s](https://www.youtube.com/watch?v=996OiexHze0&t=3416s) | corroborated | OK |
| n17 | **Aged recommendation (temporal divergence - see below).** The talk tells you to use the **implicit flow** for single-page apps because they lack a back channel. | `visuals/frame_2660.jpg` + `visuals/frame_2520.jpg` - both present implicit as the standing answer for front-channel-only clients | narration "This is a situation where you don't have a back channel, so you have to use the implicit flow" @ [&t=3632s](https://www.youtube.com/watch?v=996OiexHze0&t=3632s) | divergence (temporal) | **needs-check - do not apply** |
| n18 | Native mobile apps use the **OIDC authorization code flow plus PKCE** (Proof Key for Code Exchange, "pixie"), with the platform details abstracted by the AppAuth library. | `visuals/frame_3570.jpg` - slide "Example: native mobile app", arrow labelled "OpenID Connect (code flow + PKCE)" | narration "you would use the OpenID Connect authorization code flow plus one extra little extension called PKCE, Proof Key for Code Exchange, sometimes called Pixie" @ [&t=3562s](https://www.youtube.com/watch?v=996OiexHze0&t=3562s) | corroborated | OK |
| n19 | Delegating login to an authorization server **decouples the authentication system from the application**, so each can be maintained and evolve separately - the durable architectural argument for adopting these protocols at all. | (no dedicated slide) | narration "now the authentication system and the rest of the app are kind of a little abstracted ... they can evolve separately if they need to" @ [&t=3527s](https://www.youtube.com/watch?v=996OiexHze0&t=3527s) | single-leg | needs-check |
