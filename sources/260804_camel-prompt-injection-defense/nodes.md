# Knowledge nodes - CaMeL (Defeating Prompt Injections by Design)

> Persona: **fact-checker** - re-adopt when working this file.

> Each node has a **stable ID** (`n1`, `n2`, ... - never renumber), a claim, **both legs each with
> its own citation** (or one leg marked `single-leg`), a gate verdict, and a confidence.

> **The gate note that governs every efficacy number below.** CaMeL's headline results are measured
> on **AgentDojo**, and **Debenedetti is first author of both papers while Tramèr co-authors both**
> (`d1`). Under the independence rule that is the same leg wearing a different hat, so no number here
> counts as third-party validation. **The design claims are unaffected** - a described architecture is
> checkable against its own figures regardless of who benchmarked it - which is why the design nodes
> are `corroborated` and the efficacy nodes are `needs-check`.

## Nodes

| ID | Claim (crux) | Evidence leg + citation | Corroborating leg + citation | Gate | Confidence |
|---|---|---|---|---|---|
| n1 | **The design thesis: secure the system around the model rather than the model itself.** CaMeL "creates a protective system layer around the LLM, securing it even when underlying models are susceptible to attacks" | Abstract, p1 | §11 Conclusion, "we have shown that it is possible to design a system around an untrusted model that makes the whole system robust even if the model itself is not", p24 | corroborated | OK |
| n2 | **Dual LLM protects control flow and leaves data flow exposed**, which is the gap CaMeL exists to close. An injection that cannot change the *plan* can still change a tool call's *arguments* | `visuals/fig2_dataflow_diverted.png` - the plan is unchanged and correct, while the extracted document name and recipient address are both attacker-chosen, ending in "Send confidential.txt to attacker@gmail.com" | §2, "while the *control flow* is protected by the Dual LLM pattern, the *data flow* can still be manipulated. This is analogous to an SQL injection attack in which an adversary manipulates the query parameters rather than the structure of the query itself", p3 | corroborated | OK. **The cleanest statement of the problem in the source** |
| n3 | **The architecture: a Privileged LLM sees only the user query and writes code; a Quarantined LLM parses untrusted data and holds no tools.** The P-LLM never sees tool output - values are stored in variables and it manipulates the variable, never its content | `visuals/fig5_architecture.png` - P-LLM generates code from the user query only; Q-LLM processes untrusted data behind `query_quarantined_llm(...)` with an `output_schema`; the interpreter sits between them | §5.1, "the P-LLM only interacts with the user query and not the data returned by tools or with the Q-LLM output: values returned by tools are stored in variables, and the P-LLM can only see the code it generated and not the variable's content", p7 | corroborated | OK |
| n4 | **The Q-LLM cannot talk back in free text**, which closes the obvious re-injection path. It returns only schema-conforming structured output plus one boolean `have_enough_information` | §5.1, "the Q-LLM cannot communicate to the P-LLM what information it needs, as this could be a vector for prompt injections", p7 | `visuals/fig5_architecture.png` - the Q-LLM call carries an `output_schema=EmailStr` argument and returns into a variable rather than into the prompt | corroborated | OK. **A small design detail doing large security work** |
| n5 | **Capabilities are metadata on every value, recording provenance (sources) and permitted readers**, and they are checked when a tool is called rather than when data is read | `visuals/fig5_architecture.png` - the data-flow graph table with Value / Readers / Sources columns, feeding "Enforce policies based on capabilities" | §5.3, "capabilities consist of tags assigned to each individual value that describe control and data-flow relationships ... The current implementation of CaMeL tags data with information on data provenance and a set of allowed readers", p9 | corroborated | OK |
| n6 | **Security policies are arbitrary Python functions returning Allowed or Denied**, deliberately not a DSL | §5.2 with Figure 6, "We opted to use Python code over a custom DSL to allow for arbitrary logic to be implemented within the policy", p9 | Figure 6, p8 - a working calendar-event policy that checks `can_readers_read_value` over the title against the participant set | corroborated | OK |
| n7 | **The interpreter builds a data-flow graph as it executes**, so a value's full dependency set is known at the moment a tool is called | `visuals/fig7_code_depgraph.png` - generated code beside its dependency graph, where `send_email` depends on `date` because a conditional on `query_ai_assistant` gates it | §5.4, "While executing the code, the CaMeL interpreter also tracks the dependencies of each variable ... the entire dependency graph of a variable is built by recursively traversing all its dependencies", p10 | corroborated | OK |
| n8 | **Control-flow dependencies are tracked in a STRICT mode because a conditional leaks information**, and the paper offers a NORMAL mode that does not, as an explicit security-utility dial | `visuals/fig7_code_depgraph.png` - the caption states the STRICT-mode graph adds the `send_email` to `date` edge "to account for the fact that the call to send_email depends on the conditional given by the call to Quarantined LLM, and hence could reveal side-channel information" | §5.4, "the CaMeL interpreter has two interpretation modes: a STRICT and a NORMAL mode", p10 | corroborated | OK |
| n9 | **Headline efficacy: 77% of AgentDojo tasks solved with provable security, against 84% undefended** - roughly a 7-point utility cost for a security guarantee | Abstract, "solving 77% of tasks with provable security (compared to 84% with an undefended system) in AgentDojo", p1 | §6.1, the utility evaluation, p13 | **needs-check** | **Authors' own benchmark** (`d1`) |
| n10 | **Successful attacks fall from roughly 100 to about 10 with isolation alone, and to 0-1 once policies are added**, while utility under attack is nearly unchanged | `visuals/fig9_security_results.png` - left panel shows utility under attack tracking the undefended bar across six models; right panel is a log-scale attack count where blue (native tool calling) sits at 100-300 and CaMeL bars sit at 0-1 | §6.2, the security evaluation, p14 | **needs-check** | Authors' own benchmark (`d1`), and the effect size is large enough that the direction is unlikely to be an artifact |

## Dropped / divergences (audit trail)

| Candidate | Verdict | Note |
|---|---|---|
| `d1` - **the benchmark is the authors' own** | **divergence, and the governing one** | Every efficacy number in this source is measured on **AgentDojo**, whose first author is **Debenedetti** - also CaMeL's first author - and which **Tramèr** also co-authors. Nothing is concealed and the citation is normal. Under this kit's independence rule it still means the evaluation is **not third-party validation**, so `n9`, `n10` and `n11` are gated `needs-check` despite large effect sizes. **This is why S19 (AgentDojo) is being ingested separately** rather than accepted through this paper |
| `d2` - "provable security" against "formal verification is future work" | **divergence** | The abstract says CaMeL solves 77% of tasks "with provable security" (p1), while §10 states that formal verification of CaMeL and its security properties is "a crucial direction for future work" (p24, `n19`). Both are defensible on a charitable reading - *provable* plausibly means "the policy decision is decidable from the data-flow graph" rather than "we proved it" - and the abstract is the sentence that travels. **Finding, kept**: read "provable" as *enforceable by construction*, not as *verified* |
| `d3` - the baseline defences were implemented by the proposers | noted | §6.3's comparison against tool filters, Spotlighting and instruction hierarchy is run by CaMeL's authors on CaMeL's authors' benchmark. Disclosed and ordinary, and it compounds with `d1` rather than being separate from it |
| Vendor position | noted | Google + Google DeepMind + ETH Zurich. The artifact is academic, and the thesis - that **scaffolding around an untrusted model beats trying to make the model robust** - is one that favours a platform provider over a model provider. Not a reason to discount it; a reason to notice who benefits if it is adopted |
| Figures 1, 3, 4, 6, 8, 10, 11, and the ~100-page appendix | dropped | Figure 6 (a policy as Python) is **cited in `n6` as a read artifact but not kept**, since `LEARNING.md` teaches policy expressiveness in prose and a code screenshot would be archiving. The appendix is system prompts, per-suite tables and generated-code transcripts - replication material |
| Companion repo `github.com/google-research/camel-prompt-injection` | not gated | Not cloned. **For this source a docs-versus-code pass would be worth more than usual**, because the entire security argument rests on the interpreter's behaviour and the interpreter is published |
