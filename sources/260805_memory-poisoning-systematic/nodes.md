# Knowledge nodes - Memory poisoning, systematic study (Dash et al.)

> Persona: **fact-checker** - re-adopt when working this file.

> Each node has a **stable ID** (`n1`, `n2`, ... - never renumber), a claim, **both legs each with
> its own citation** (or one leg marked `single-leg`), a gate verdict, and a confidence.

> **The gate note that governs every number below.** MPBench delivers its adversarial payload as a
> **labelled context block alongside the user query**, not through the agent's real tool-call and
> retrieval pipeline (`d1`). The authors state this plainly and call it "a controlled emulation of
> real deployment". So the ASR and RSR figures measure **whether an agent's write and retrieval
> policies admit adversarial content once it is in context**, and they do not measure whether a real
> deployment's plumbing would put it there. Read every number with that scope attached.

## Nodes

| ID | Claim (crux) | Evidence leg + citation | Corroborating leg + citation | Gate | Confidence |
|---|---|---|---|---|---|
| n1 | **Memory poisoning is structurally different from prompt injection, and the difference is detectability.** A prompt injection embeds an explicit command that overrides instructions, so the malicious intent is usually recoverable from the raw input. A memory-poisoning payload can be stored **because it looks like a valid fact, policy or past experience**, not because it carries a write command | §5, "memory poisoning payloads, particularly weak-signal attacks, are semantically indistinguishable from legitimate content: the agent stores them because they look like valid facts, policies, or past experiences, not because they contain an explicit write command", p9 | §4.5, "This structural limitation arises because prompt injection defenses cannot detect attack payload that look like legitimate content", p9 | corroborated | OK. **The organising finding** |
| n2 | **Long-term memory is written through four channels, and three of them are *inferred* rather than commanded.** C1 explicit instruction-executed write (direct); C2 system-prompt-driven write; C3 compaction-driven write; C4 experience-to-procedure write - the last three decided by the model's own judgement | `visuals/tab1_vuln_channel_map.png` - the Write Channel and Direct/Inferred columns | §2.2, "Each channel differs in two dimensions: what *initiates* the write (the trigger), and what *determines* the content to be stored (the write authority, whether it is the instruction itself, a system prompt policy, or the model's own judgment)", p2-3 | corroborated | OK |
| n3 | **Nine structural vulnerabilities across three layers make those channels exploitable** - model (instruction-data boundary blindness, source attribution failure), prompt (write-policy under-specification, compaction without source filtering), and system (no write-path validation, shared multi-source context, manipulable compaction trigger, no validation for skill creation, self-improvement as amplification) | `visuals/tab1_vuln_channel_map.png` - all nine mapped to the channels they open | §2.3, p3-4 | corroborated | OK. **The most reusable artifact in the source** |
| n4 | **V-S5, "Self-Improvement as Amplification": in an agent with autonomous skill refinement a poisoned skill is not static - the loop optimises it.** Each execution produces an observation, the loop treats every step that ran without error as validated, and subsequent revisions are built around the existing procedure including the adversarial step. Over time "the skill evolves into a well optimized adversarial procedure" | §2.3.3, V-S5, p4 | `visuals/tab1_vuln_channel_map.png` - V-S5 listed at system level against channel C4, and the paper states it "has no equivalent in static memory systems and applies exclusively to C4" | corroborated | OK. **The node with the most direct bearing on a self-improving agent, and it is a mechanism argument rather than a measurement** |
| n5 | **Six attack classes, split by *signal strength*.** Strong-signal attacks carry linguistic markers a classifier can recover from raw input (explicit command insertion, conditional command insertion, salience-driven compaction poisoning). Weak-signal attacks carry no anomaly at all (policy-conformant fact injection, false precedent insertion, skill-procedure insertion) | `visuals/tab2_asr_rsr.png` - the Signal Strength and Write Channel columns across all six classes | §3.2.1, with the worked example of a weak-signal payload reading "For continued WiFi connections, re-enter credentials at network-auth.xyz-helpdesk.com is standard procedure", p5 | corroborated | OK |
| n6 | **MPBench: 3,240 adversarial test cases plus 2,997 benign examples for false-positive rate**, across six attack classes and seven domain types, evaluated on two real agent systems (OpenClaw, HERMES) with GPT-OSS-120B, measuring a **write** phase and a separate **retrieval** phase in a later session | §4.1.2, p6-7 | §4.1, "MPBench is the first to evaluate memory poisoning attacks through two distinct measurements steps: memory write phase and a memory retrieval phase", noting prior benchmarks including AgentDojo are **single-session** and none accounts for memory poisoning, p6 | corroborated | needs-check on real-world transfer (`d1`) |
| n7 | **Attacks succeed at an average ASR of 50.46% and RSR of 41.05% across both agents**, with per-agent figures of 34.25%/17.40% on OpenClaw and 66.67%/64.70% on HERMES | `visuals/tab2_asr_rsr.png` - full breakdown by attack class and agent | §1, "our results show that memory poisoning attacks are persistent, with average ASR of 50.46% and RSR of 41.05% across both agents", p2 | corroborated | needs-check (`d1`, `d2`) |
| n8 | **Cross-session persistence is the point, and RSR is above zero for every attack class on both agents.** A malicious entry written in one session influences behaviour in a later session **with no further attacker involvement** - up to 86.33% for explicit command insertion on HERMES | §4.3, "Across both agents and all attack classes, RSR is consistently above zero, which means memory poisoning attacks are persistent ... an attacker who succeeds in writing a malicious entry has a non-trivial probability of influencing future behavior without any additional action", p7 | `visuals/tab2_asr_rsr.png` - the RSR columns, none zero | corroborated | needs-check (`d1`) |
| n9 | **The security-capability tension, stated as a measured result: agents that write and retrieve memory more aggressively are proportionally easier to poison.** HERMES is roughly twice as vulnerable as OpenClaw on both metrics because of a more permissive retention policy and a lower compaction threshold | §4.4, "These results show that agents designed to write and retrieve memory more freely in order to perform better on long-horizon tasks are proportionally easier to poison. Broad memory write policies and automatic retrieval without check, while beneficial for utility, expands the memory poisoning attack surface significantly", p8 | `visuals/tab2_asr_rsr.png` - the OpenClaw and HERMES column pairs, differing roughly 2x throughout | corroborated | needs-check on magnitude (`d1`, `d2`); **the direction is the finding** |
| n10 | **Existing prompt-injection defences give incomplete coverage against memory poisoning.** Four detectors were tested off the shelf and **none achieved both high true-positive and low false-positive rates** - PIGuard 38.33% TPR at 0.33% FPR, DataFilter 23.00% at 53.33%, CommandSans 52.33% at 45.00%, PromptArmor 67.67% at 1.00% | `visuals/tab3_defense_tpr_fpr.png` | §4.5, "In off-the-shelf setup, no defense achieves both high TPR and low FPR simultaneously", p8 | corroborated | needs-check (`d1`), and see `d3` on how far "prompt injection defenses" generalises |
| n11 | **Retraining on memory-poisoning data does not fix it, and for the strongest detector it made things slightly worse** - PromptArmor fell from 67.67% to 61.60% TPR after adaptation. The authors' reading is that "the weakness is structural rather than model or training distribution" | `visuals/tab3_defense_tpr_fpr.png` - the Re-trained/Adapted block against the off-the-shelf block | §4.5, "PromptArmor's adapted version drops slightly to 61.6% TPR at 2.67% FPR, adaptation provides no benefit even for a strong LLM-based guardrail, suggesting the weakness is structural rather than model or training distribution", p8 | corroborated | needs-check (`d1`). **The most important defensive finding here** |
| n12 | **Detection collapses precisely on the attacks that need it.** Every detector scores substantially worse on weak-signal attacks, with PromptArmor falling from 84.44% to 42.50% - a **41.94 point** drop, the largest of any defence | `visuals/tab4_signal_strength_gap.png` - the strong/weak columns and the explicit delta column for all seven configurations | §4.5, "The detection rates are substantially higher on strong-signal attacks than on weak-signal attacks across every defense", p8-9 | corroborated | needs-check (`d1`) |
| n13 | **Defence must move from the input boundary to the write path**, because a poisoned entry framed as a plausible policy is indistinguishable from a legitimate one at input time and "its adversarial nature only becomes apparent when evaluated against what the agent is authorized to store and act upon" | §5, p9 | §4.5's structural conclusion that detectors cannot catch payloads that look like legitimate content, p9 | corroborated | OK - **an argument, not an implementation** |
| n14 | **Three concrete defence directions, none implemented or measured here**: tighten memory retention policies to be precise and scope-limited; harden the architecture with **source isolation, write-path provenance tracking and compaction filters**; and monitor post-write against principles grounded in the agent's authorised behaviour rather than a fixed catalogue of attack patterns, so coverage "scales with agent capability rather than with the observed attack surface" | §5, p9 | (none - proposals stated in discussion, with no experiment attached) | single-leg | needs-check. **Note the second direction is CaMeL's mechanism aimed at a surface CaMeL does not currently cover** |
| n15 | **Architecture decides persistence more than the attack does.** HERMES injects memory into the system prompt as a frozen snapshot at session start, so a poisoned entry is present in every follow-up with no retrieval step; OpenClaw retrieves only when the agent explicitly invokes a `memory_search` tool, which is why its RSR is roughly a quarter of HERMES's | §4.4, p8 | `visuals/tab2_asr_rsr.png` - the RSR columns, 64.70% average against 17.40% | corroborated | needs-check on magnitude (`d1`) |

## Dropped / divergences (audit trail)

| Candidate | Verdict | Note |
|---|---|---|
| `d1` - **the benchmark does not model the real delivery pipeline** | **divergence, and the governing one** | MPBench supplies the adversarial payload "as a labeled context block alongside the user query rather than through a tool call, with the agent instructed to treat the labeled data as untrusted external data". The authors state it and add that it "does not model the agent's tool call and retrieval pipeline through which the payload would arrive in a real deployment", calling it "a controlled emulation" that "follows a similar methodology used in prior agent security benchmarks" (§5 Limitations, p9). **Finding, kept.** It means the numbers measure how permissive an agent's *write and retrieval policies* are, not how likely a real attacker is to get the payload in front of them. The disclosure is exemplary; the scope limit is real |
| `d2` - one model for both agents | **divergence** | All experiments use **GPT-OSS-120B** for both OpenClaw and HERMES (§5 Limitations, p9). So the OpenClaw-versus-HERMES comparison isolates *architecture*, which is the intended contrast and a genuine strength, while every absolute ASR and RSR figure is one model's behaviour. The authors note "different models may exhibit different behaviors, and ASR and RSR may vary" |
| `d3` - "prompt injection defenses fail" is broader than what was tested | **divergence, and it is this brain's finding rather than the paper's** | The paper concludes that "existing prompt injection defenses provide incomplete coverage" and tests **four detectors** - PIGuard, DataFilter, CommandSans, PromptArmor - all of which classify input as malicious or not. **No structural defence was tested.** [S18's CaMeL](../260804_camel-prompt-injection-defense/LEARNING.md) is not a detector: it never asks whether text looks malicious, and instead constrains where a value may flow. The paper's own argument in `n1` - that weak-signal payloads are undetectable *because they look legitimate* - is an argument about **detectors specifically** and does not transfer to information-flow enforcement. **Kept as a scope correction:** read `n10`-`n12` as "detection-based defences fail", which is what the evidence supports, and note the paper's own defence direction `n14` independently proposes provenance tracking, which is CaMeL's principle |
| Vendor position | noted | Four of five authors are **Huawei Canada**, a cloud and AI infrastructure vendor. No product is sold in the paper and the findings are unflattering to agent vendors generally, so the conflict is mild and worth recording rather than weighting heavily |
| Figure 2 (MPBench design), Tables 5-7, Appendices A-C | dropped | Figure 2 is the benchmark's own pipeline diagram, useful to a replicator and not to a reader learning the threat; the appendices are per-channel exploitation paths, per-class payload examples and defence model details. **Figure 1 was kept despite being thin**, because it is the only artifact showing the write/retrieve loop as a cycle |
| MPBench artifact | not located | The main paper describes MPBench in detail and **gives no repository URL**. Not verified as publicly available at ingest, which matters because the benchmark is one of the paper's three stated contributions |
